# 多模态数据湖仓核心业务流与前端 UI 底座优化设计

日期：2026-06-08  
状态：待评审  
范围：前端信息架构、UI 底座、核心业务流页面重组  

## 1. 背景

当前前端的问题不是单纯“页面不好看”。从项目结构和实现状态看，主要问题集中在四类：

- 信息架构分散：接入、查询、编排、任务、资产目录之间有页面入口，但用户完成一条真实数据链路时需要自行理解跳转关系。
- UI 语言混杂：项目同时使用 Arco 原生样式、`styles.css`、`prd-style.css` 和大量页面级 class，页面之间不像同一个产品。
- 页面职责过重：`LakeQueryPage.jsx`、`IngestionWorkbenchPage.jsx`、`DataGovernancePage.jsx` 等文件偏大，功能、布局、状态和演示数据耦合在一起。
- 中文文案/编码风险：源码和终端输出中存在明显中文乱码，影响导航、按钮、空状态、错误提示和交付文档可信度。

本轮采用“核心业务流优先 + UI 底座先行”的方案。目标不是先做全站换皮，而是让核心链路更好用，并让后续页面可以按同一套结构持续演进。

## 2. 目标与非目标

### 目标

1. 建立一条清晰的核心工作流：
   `数据接入/上传 -> 检索与 SQL 查询 -> 工作流编排 -> 任务治理 -> 资产目录/版本/血缘`
2. 收口最小 UI 底座：
   应用壳、导航命名、页面标题区、指标卡、筛选区、表格、详情抽屉、空状态、加载状态、错误状态。
3. 优先重构关键页面：
   `App.jsx`、`LakeQueryPage.jsx`、`IngestionCenterPage.jsx`、`WorkflowCenterPage.jsx`、`TaskCenterPage.jsx`、`FilesPage.jsx`。
4. 降低页面复杂度：
   把大页面拆成页面容器、业务组件、状态/数据适配层和纯展示组件。
5. 处理中文文案一致性：
   导航、页面标题、按钮、状态、空态、错误提示统一为可读中文，避免乱码继续扩散。

### 非目标

1. 本轮不迁移到 Umi、Ant Design Pro 或其他新框架。
2. 本轮不重写后端 API。
3. 本轮不一次性重做所有页面。
4. 本轮不以大屏汇报页为主目标；汇报效果作为核心链路稳定后的增强层。
5. 本轮不引入新的全局状态管理库，除非实现阶段证明现有状态方式无法支撑。

## 3. 方案选择

### 方案 A：全站 UI 先换皮

优点是视觉见效快，改动主要集中在样式和通用布局。缺点是业务链路仍然分散，功能深度不足的问题不会真正消失。

### 方案 B：核心业务流优先，补齐最小 UI 底座

优点是能同时改善可用性和观感，把用户真实工作路径作为设计中心。缺点是需要先梳理页面关系和关键状态，工作量高于单纯换皮。

### 方案 C：汇报演示页优先

优点是短期展示效果好。缺点是容易留下真实使用链路和组件体系的技术债。

### 选定方案

采用方案 B，并在第一阶段吸收方案 A 的最小 UI 底座。方案 C 延后到核心链路稳定后执行。

## 4. 信息架构

侧边导航按用户任务组织，而不是按历史页面堆叠：

1. 总览
   - 湖仓总览
   - 最近任务
   - 关键告警
2. 数据接入
   - 接入总览
   - 来源接入
   - 本地上传
   - 接入任务
3. 查询与检索
   - SQL 查询
   - 统一检索
   - 向量检索
   - 多模态检索
   - AI 数据副驾驶
4. 编排与计算
   - 工作流编排
   - 算子中心
   - 作业实例
   - 模板库
5. 任务治理
   - 全部任务
   - Ray 作业
   - 执行日志
   - 重试/取消/导出
6. 资产目录
   - 数据集
   - 版本
   - Schema
   - 血缘
7. 运维与配置
   - 集群
   - 告警
   - 巡检
   - 系统配置
   - 用户与权限

已有路由不立即破坏性迁移。第一阶段保留兼容跳转，用新导航和新页面标题建立用户认知。

## 5. UI 底座设计

### 应用壳

`App.jsx` 负责：

- 统一导航数据结构。
- 统一面包屑和页面标题来源。
- 统一用户区、通知区、全局搜索入口。
- 支持当前路由高亮和旧路由重定向。
- 移除明显乱码文案。

应用壳视觉采用中后台工作台风格：浅色内容区、低饱和侧边栏、紧凑顶部栏、少装饰、强调扫描效率。

### 页面模板

建立三类页面模板：

1. 工作台页
   - 页面标题区
   - KPI/状态摘要
   - 主操作区
   - 最近记录/异常列表
2. 列表页
   - 页面标题区
   - 筛选工具条
   - 表格
   - 详情抽屉
   - 分页/批量操作
3. 工作流/编辑器页
   - 顶部工具条
   - 左侧资源面板
   - 中央画布或编辑区
   - 右侧配置/日志/结果面板

### 通用组件

优先沉淀以下组件：

- `PageHeader`
- `MetricStrip`
- `FilterBar`
- `DataTableShell`
- `DetailDrawer`
- `EmptyState`
- `LoadingState`
- `ErrorState`
- `StatusBadge`
- `ActionToolbar`

组件先服务本轮页面，不做过度抽象。只有两个以上页面真实复用时再提升为通用组件。

### 样式策略

- 保留 Arco 作为组件库。
- 收口 CSS token，保留必要的颜色、间距、圆角、阴影、字体变量。
- 减少页面级“PRD 风格”特殊 class 的扩散。
- 卡片圆角控制在 8px 左右，避免过度营销化视觉。
- 页面不做浮夸 hero，不使用装饰性渐变球或大面积单色系背景。

## 6. 核心页面设计

### 6.1 数据接入

涉及页面：`IngestionCenterPage.jsx`、后续可合并 `IngestionWorkbenchPage.jsx` 和 `UploadPage.jsx` 的有效能力。

设计目标：

- 接入总览展示来源数量、最近同步、失败任务、待处理文件。
- 来源接入提供连接配置、连接测试、扫描结果、同步任务入口。
- 本地上传提供文件选择、上传进度、处理策略、入湖结果。
- 接入任务直接进入任务治理视图，避免用户在多个页面之间猜测状态。

### 6.2 查询与检索

涉及页面：`LakeQueryPage.jsx`。

设计目标：

- 把 SQL、统一检索、向量检索、多模态检索、AI 副驾驶拆成清晰 tab 或子路由。
- 每个模式有独立输入区、筛选区、结果区和解释区。
- 搜索结果支持列表/网格/详情预览，显示相似度、来源、时间、标签。
- SQL 查询保留编辑器、库表辅助、执行历史和结果表格。
- AI 副驾驶作为增强入口，不替代 SQL 和检索的基础能力。

### 6.3 工作流编排

涉及页面：`WorkflowCenterPage.jsx`、`WorkflowStudio.jsx`。

设计目标：

- 工作流中心展示模板、最近工作流、运行状态和快捷创建。
- 工作流编辑器采用三栏结构：资源面板、画布、配置/日志面板。
- 节点操作使用图标按钮和工具条，减少文字按钮堆叠。
- 节点配置和执行日志在右侧面板切换，避免弹窗打断编辑。

### 6.4 任务治理

涉及页面：`TaskCenterPage.jsx`、`RayJobsPage.jsx`。

设计目标：

- 统一展示接入任务、工作流任务、Ray 作业和系统任务。
- 任务列表支持类型、状态、时间、发起人筛选。
- 详情抽屉展示基本信息、执行日志、输入输出、失败原因、重试/取消操作。
- Ray 作业保留专页深度能力，但从任务治理入口可跳转。

### 6.5 资产目录

涉及页面：`FilesPage.jsx`。

设计目标：

- 从“文件列表”升级为“数据集/资产目录”。
- 左侧为数据集/目录树，中间为资产列表，右侧为详情摘要。
- 数据集详情展示 Schema、版本、向量化配置、血缘入口和关联任务。
- 版本、血缘等能力先以可用入口和明确能力边界落地，避免假装完整实现。

## 7. 数据与 API 策略

本轮前端优先复用现有 API，不要求后端同步大改。

前端数据层按页面建立轻量适配：

- API 返回字段在 `api/` 或页面 service 层转换为 UI 模型。
- 页面组件只消费稳定 UI 模型，不直接依赖后端原始字段。
- 对暂未接通的能力使用明确的空状态或“待接入”状态，不使用误导性的假成功。
- 对超时、失败、空结果提供统一错误文案和重试入口。

## 8. 错误处理与状态

每个核心页面至少覆盖：

- 初始加载
- 加载中
- 空数据
- 局部失败
- 全页失败
- 操作成功
- 操作失败
- 权限不足

错误文案要说明发生了什么、用户可以做什么、是否需要联系管理员。不要只展示后端原始异常。

## 9. 测试与验证

实现阶段需要覆盖：

1. 构建验证：`npm --prefix frontend run build`
2. 单元测试：已有 Vitest 测试继续通过。
3. 路由验证：核心导航入口可打开，旧路由重定向不破坏。
4. 视觉冒烟：桌面宽屏、普通笔记本、窄屏下无明显遮挡和溢出。
5. 状态验证：加载、空态、错误态至少在组件层可人工触发检查。
6. 文案检查：导航、标题、按钮、空态、错误提示不出现乱码。

## 10. 分阶段落地

### 阶段 1：UI 底座与导航收口

- 整理 `App.jsx` 导航结构和文案。
- 新增页面模板和通用状态组件。
- 收口关键 token 和 Arco 覆盖样式。
- 清理核心导航、标题、用户区乱码。

### 阶段 2：核心业务流页面重组

- 重构 `LakeQueryPage.jsx`。
- 重构 `IngestionCenterPage.jsx`。
- 重构 `WorkflowCenterPage.jsx` 与工作流入口。
- 重构 `TaskCenterPage.jsx`。
- 重构 `FilesPage.jsx` 为资产目录视角。

### 阶段 3：演示效果与 polish

- 打磨总览页和关键首屏。
- 补齐跨页面快捷入口。
- 优化图表、详情抽屉、状态反馈。
- 清理冗余 CSS 和未使用样式。

## 11. 验收标准

- 核心链路可以从导航按顺序完成浏览：接入、查询/检索、编排、任务、资产。
- 所有核心页面使用统一页面标题、筛选、表格、状态和详情结构。
- 关键导航和页面文案无乱码。
- 页面不再呈现明显割裂的多套视觉风格。
- 构建通过。
- 不破坏现有登录、权限和已有 API 调用。
- 旧路由保留兼容跳转或明确替代入口。

## 12. 风险与对策

- 风险：一次性触碰页面过多。
  对策：先落 UI 底座，再逐页迁移，保证每个阶段都可构建。
- 风险：现有 API 字段不稳定或超时。
  对策：前端适配层隔离字段，统一超时/失败状态。
- 风险：样式全局影响面过大。
  对策：先新增模板 class，再逐步替换页面级样式，不做全局大删改。
- 风险：中文乱码来源复杂。
  对策：优先修复用户可见文案；提交前检查源码编码和构建输出。
- 风险：演示诉求和真实使用诉求冲突。
  对策：先保证真实链路，演示页只复用链路数据和组件，不另起一套视觉。
